# Internationalisation

Package: `packages/i18n` (`@transcendence/i18n`) — used by `front` and `studio`.

Three languages: **English** (fallback), **French**, **Spanish**. i18next +
react-i18next, with the locale files in the package rather than in either app so
one string is translated once.

## What the package exports

```ts
import {
  I18nProvider,
  LanguageSelect,
  useTranslation,
  Trans,
} from "@transcendence/i18n";
import {
  LANGUAGE_OPTIONS,
  SUPPORTED_LANGUAGES,
  FALLBACK_LANGUAGE,
  toLanguage,
} from "@transcendence/i18n";
import type { Language, TranslationKey } from "@transcendence/i18n";
```

`useTranslation` and `Trans` are **re-exported from react-i18next**, so app code
never imports react-i18next directly — same rule as antd going through
`@transcendence/ui`.

Mount `I18nProvider` high in the tree; in `apps/front` the order is
`MsnThemeProvider > I18nProvider > AuthProvider > App`.

## Three decisions worth knowing

### English is the reference, enforced at compile time

`i18n.ts` builds the resource bundle with a `satisfies` clause:

```ts
const resources = {
  en: { translation: en },
  es: { translation: es satisfies typeof en },
  fr: { translation: fr satisfies typeof en },
};
```

A key that exists in `en.json` but is missing from `fr.json` or `es.json` is a
**build error**, not a raw `some.dotted.key` rendered on screen at runtime. The
locale files currently share 17 top-level namespaces (`auth`, `chat`, `common`,
`following`, `header`, `home`, `landing`, `legal`, `music`, `nav`, `producers`,
`samples`, `sessions`, …) — `music` holds vocabulary shared by both apps, such as
note names.

`index.ts` also declares the i18next module augmentation:

```ts
declare module "i18next" {
  interface CustomTypeOptions {
    resources: { translation: typeof en };
  }
}
```

That is what makes `t('samples.title')` type-checked. It is declared in `index.ts`
rather than a standalone `i18next.d.ts` on purpose — a `.d.ts` nothing imports is
never pulled into an app's TypeScript program, so it would silently do nothing.

`TranslationKey` (`ParseKeys`) is the type to use when a static data file needs to
_store_ a key instead of a string, so a stale key fails the build too.

### The language change fans out to three places

`t()` is not the only thing that has to follow the language. An i18next
`languageChanged` listener applies the rest:

```ts
function applyLanguage(language: string) {
  document.documentElement.lang = language; // a11y, and the browser's own hyphenation
  setDateLocale(language); // @transcendence/date → dayjs
}
```

and `I18nProvider` wraps children in a second antd `ConfigProvider` carrying
`antd/locale/{en_US,fr_FR,es_ES}` — antd owns strings our JSON never sees (Table
"No data", Pagination, DatePicker). **Nested antd `ConfigProvider`s merge**, so
setting only `locale` here inherits the theme from `MsnThemeProvider` above and
`packages/ui` needs no change.

The listener is also called once at init, because it never sees the language the
detector just picked.

### Detection is localStorage, then the browser

```ts
detection: { order: ['localStorage', 'navigator'], caches: ['localStorage'],
             lookupLocalStorage: 'msn.locale' }
load: 'languageOnly'
```

An explicit choice wins over the browser's preference and survives a reload.
`load: 'languageOnly'` collapses regional variants — `fr-CA` and `es-419` resolve
to the base language we actually ship, instead of falling through to English.

`LANGUAGE_OPTIONS` labels each language **in its own language** ("English",
"Français", "Español"), so a visitor who cannot read the current UI can still find
theirs.

## What deliberately stays in English

Not every string on screen is a translation candidate. These are decisions, not
oversights — don't "fix" them without changing the decision first.

**Server error details.** `apiError` (`packages/auth/src/api.ts`) surfaces the
backend's own message, and `apps/back` writes those in English
("Maximum storage capacity reached", "Avatar file is too large"). Roughly a dozen
call sites render it as the _detail_ of a notification or `Result` whose **title
is translated** — the title carries the meaning, the detail carries the specifics.
Translating them would mean the backend returning an error `code` that the front
maps to a key; worth doing if the error surface grows, not before.

**Sample taxonomy, but not musical vocabulary.** `Family` and `Kind`
(`apps/front/src/types/sample.ts`) are rendered as their raw values — `KICK`,
`SNARE`, `ONE-SHOT`, `LOOP` — because producers read them as English jargon in
every DAW they use, so they get no translation keys (`FAMILY_OPTIONS` /
`KIND_OPTIONS` in `pages/Samples/helpers.ts` label themselves).

Note names and modes are the exception and **are** translated: French and Spanish
name notes in solfège, so a `Key` renders `C♯` in English and `Do♯` in French, and
`MAJOR` becomes `Majeur` / `Mayor`. The letter maps to `music.note.{a..g}`, the
accidental stays a symbol (♯ / ♭ are universal), and `Mode` maps to
`samples.mode*`.

Both apps need this, so `Key`, `Mode` and their formatters live in
`packages/i18n/src/music.ts` — the one part of the audio domain the i18n package
owns, because these values only exist on screen in translated form. The front
re-exports `Key` / `Mode` from `types/sample.ts` so that file stays the single
door to the sample domain types. Because the formatters need `t`,
`formatKey(key, t)` takes it as an argument and the option arrays are
**functions** — `keyOptions(t)`, `modeOptions(t)` — not module-level consts
frozen before a language is known. That is also why the package re-exports
`TFunction`.

**Everything the effects rack labels.** In `apps/studio/src/ui/Devices/`, the knob
and toggle labels (`Thresh`, `Atk`, `Rel`, `Feedbk`, `Pre-Dly`, `Dry`, `Wet`, …),
the device names in `effectFactories.ts` (`Noise Gate`, `Dattorro Reverb`,
`Tremolo / Autopan`) and their families (`dynamics`, `distortion`, `space`,
`stereo`, shown uppercased in the browser's Devices tab) all stay in English —
same reasoning as the sample taxonomy above, and the abbreviations are the
convention in every DAW. Some are not ours to translate anyway: `MsnParamToggle`
falls back to `param.name` and `MsnParamKnob` prints `print.unit`, both supplied
by the `@opendaw/*` SDK. `MASTER … dB` in the meter and the `M` / `S` pills on a
track are in the same bucket.

**Legal pages.** `pages/{Legal,Privacy,Terms}` ship one component per language
(`Legal.fr.tsx`, …), picked in the page wrapper from `i18n.resolvedLanguage`.
Long legal prose does not belong in a JSON bundle — the paragraph structure
itself differs between jurisdictions.

**Placeholder content.** Mock data still awaiting its endpoint (`home.data.ts`
activity feed and presence rows, `SESS_GENRES`) and dev markers
(`ImagePlaceholder` labels like `HERO_SCREENSHOT — …`) are left in English: they
are due to be deleted, and keys for them would be dead weight. Form example
placeholders (`you@example.com`, `lexmoreau`) are in the same bucket.

## Terminology

Same word, same translation, everywhere. The mistakes this table prevents were all
real ones — three renderings of _liked_ on three screens, `track` translated twice
in the same nav.

| Concept                              | EN            | FR                                   | ES               |
| ------------------------------------ | ------------- | ------------------------------------ | ---------------- |
| A published, exported piece of music | track         | **track** (fem.: _une track_)        | **tema**         |
| A lane in the studio timeline        | track         | **piste**                            | **pista**        |
| The effects/instrument panel         | Devices       | **Devices**                          | Dispositivos     |
| Muting a device in the chain         | Bypass        | **Bypass**                           | **Bypass**       |
| Marking a track as liked             | Like / Unlike | **Like / Unlike**, _une track likée_ | Me gusta         |
| The `@` identifier                   | handle        | **pseudo**                           | alias            |
| The public producer name             | artist name   | **nom d'artiste**                    | nombre artístico |
| Sending a file to the server         | upload        | **upload / uploader**                | subir            |
| A repeated audio phrase              | loop          | **loop**                             | loop             |

Two rules behind it:

**English words that French and Spanish producers already use stay English.**
_Like_, _bypass_, _loop_, _upload_, _track_, _devices_ are the words spoken in a
studio; translating them ("Aimer", "Contourner", "Appareils") makes the UI read
like a machine translation of a product nobody uses. This is the same reasoning as
the sample taxonomy above, applied to verbs and UI nouns instead of data values.

**Track vs. piste is a real distinction, not a synonym.** A _track_ is the thing
you export and other people play; a _piste_ / _pista_ is a lane in the arrangement.
Spanish separates them as **tema** vs. **pista**. Picking one word for both, in
either language, makes `tracks.delete.body` and `studio.addTrack.label` sound like
they are about the same object.

Two more conventions the locale files hold to:

- **French vouvoies.** The whole UI says _vous_. A `t()` string written with _tu_
  ("Réessaie", "Choisis un nouveau nom") is a bug, not a style.
- **French uses the typographic apostrophe `’`**, never `'`, and `…` rather than
  `...`. Mixed apostrophes inside one screen are visible.

## Adding a string

1. Add the key to `packages/i18n/src/locales/en.json`, inside the namespace of the
   page or feature that uses it.
2. Add it to `fr.json` and `es.json` — the build fails until you do.
3. Use it: `const { t } = useTranslation(); t('namespace.key')`.

For copy containing markup or a link, use `<Trans>` rather than concatenating
translated fragments — word order differs between languages and concatenation
cannot express that.
